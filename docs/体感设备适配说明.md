# Tentacle HRV「体感设备适配」适配说明

> 本文件由 t2《可行性与方案设计》落盘，并按 t3（固件 Profile 框架实现）更新为与当前代码一致。
> 关联代码：`esp32_firmware/esp32_firmware.ino`、`esp32_firmware/toy_profiles.h`、`esp32_firmware/toy_profiles.cpp`
> 需求出处：Koishi 论坛 topic/13546 第 7 楼（amlyxts：「哥们能用吗，不能的话可以能否适配其它体感设备」）、第 8 楼（楼主「等我做体感设备 B兼容吧」）

## 1. 结论先行

**可行，但分两层看待：**

- **层一（软件/固件架构层）—— 已实现 ✅**
  ESP32 玩具通道已从"写死常量"重构为 **设备类型 Profile 表**（`toy_profiles.h/.cpp`），
  体感设备 A（`TOY_PROFILE_JUMP_EGG`）是默认 profile，UUID/上限/报文与旧固件**逐字节一致**；
  体感设备 B类预留 `TOY_PROFILE_MALE_MST` 骨架（占位 UUID + 未实现编码），等实物逆向后填协议即可。
  后端 `server.py` / 前端 `templates/` **零改动**（它们只发 `SET 强度 时长 波形` / `STOP` 抽象指令）。

- **层二（具体机型 BLE 协议）—— 需实物/文档，当前只落模板 ⏳**
  各家体感设备 B的 GATT UUID、数据包、伸缩/振动/气压/加热通道编码互不相同且多为私有。
  无实物时**禁止**凭猜测写死协议字节。两条可行路径：
  - 实物到货 → nRF Connect 抓包逆向 → 按本文件 §6「接入步骤」填一个 profile；
  - 或选用 buttplug(stpihkal) 已文档化机型（Lovense / Kiiroo / Fleshlight Launch 等）→ 仍建议实物联调验证。

---

## 2. 为什么"体感设备 A = 默认 profile"而不是特例

旧固件整条玩具链路 = 一台 BLE 设备 + 单写特征 + 单强度值：
`SET/STOP → handleSerialCommand() → sendToToy() → toyChar->writeValue(packet)`。
体感设备 A就是这条链路的默认物理形态。因此新框架把体感设备 A建模为 **默认 profile 表项**，
并保证它的 UUID（`0000FFE0-…`/`0000FFE1-…`）、强度上限（60）、
报文（`{0xA1, 0x02, level, A1^02^level, 0xB3}`）与原实现完全一致——
**不选择 = 无感**，这是硬性回归门槛（见 §7 编译验证）。

## 4. 已实现的固件架构

```
串口 SET/STOP（server.py 原样下发）
        │
        ▼
handleSerialCommand()            // 不变：解析、constrain、scheduleStop
        │  constrain 上限取 toyActiveProfile()->max_intensity
        ▼
sendToToy(intensity, waveform)   // 分派：toyActiveProfile()->encode(...)
        │
        ▼
toy_profiles.cpp 中 profile->encode()   // 产出待写字节（体感设备 A=5 字节报文）
        │
        ▼
toyChar->writeValue(buf, len)    // 同一底层写调用
```

### 4.1 文件与职责

| 文件 | 内容 |
|---|---|
| `esp32_firmware/esp32_firmware.ino` | 顶部 `ACTIVE_TOY_PROFILE` 宏（默认 `TOY_PROFILE_JUMP_EGG`）；`g_active_profile_id` 初值；扫描/连接回调改从活动 profile 取 UUID；`sendToToy()` 按 profile 编码分派；时长停止/波形解析等**全部保留原逻辑** |
| `esp32_firmware/toy_profiles.h`（新增） | `ToyProfileId` 枚举、`TOY_CH_*` 通道位掩码、体感设备 A常量（UUID/上限）、体感设备 B占位 UUID 宏、`ToyProfile` 结构与 `encode` 函数指针、`toyActiveProfile()` 声明 |
| `esp32_firmware/toy_profiles.cpp`（新增） | profile 表（含体感设备 A完整实现 + 体感设备 B预留骨架）与两个编码器 |
| `server.py` / `templates/index.html` / `events.json` | **不改**（SET/STOP 语义对两种设备同义：强度/时长/波形） |

### 4.2 Profile 设计要点

- `ToyProfile` 字段：`id / name / service_uuid / tx_uuid / rx_uuid(可空) / max_intensity / channels(TOY_CH_*) / encode`；
- **体感设备 A（JUMP_EGG）**：`service=0000FFE0-…`、`tx=0000FFE1-…`、`max=60`、`channels=TOY_CH_VIB`；
  `jumpEggEncode()` 复刻原 `{A1 02 level xor B3}` 5 字节（含 XOR 校验与尾字节 0xB3）；
- **体感设备 B（MALE_MST，预留）**：UUID 为全 0 占位宏（`*_PLACEHOLDER`，带 TODO 注释），
  `maleMstEncode()` 直接 `return 0` —— 主循环收到后打印"预留未实现/无动作"，**不发送任何字节**；
- 强度钳制从写死的 `MAX_INTENSITY` 宏改为 `toyActiveProfile()->max_intensity`（体感设备 A时=60，行为不变）；
- 连接日志、发送日志、`✅ 执行` / `⏹ 已停止` 等文案均保持原样。

## 5. 协议调研速览（stpihkal / buttplug，作为未来 profile 参照）

> stpihkal 内容为 CC BY-NC-SA 4.0，以下仅概括并附出处链接，不整段搬运。

| 品牌/机型 | 传输 | 控制形态 | 男用？ | 对本框架的启示 |
|---|---|---|---|---|
| Lovense（Max/Calor/Solace…） | BLE GATT | 分号文本指令 `Vibrate:0-20;` `Rotate:10;` `Air:Level:3;` 等；三代服务 UUID（一代 0xFFF0 族 / 二代 Nordic / 三代可变） | Max/Solace/Calor 是 | 强度档位不同（0-20/0-5），需 profile 带换算；多通道（振动/气压/旋转）→ 单强度语义映射 |
| Kiiroo Onyx 2 / Fleshlight Launch | BLE GATT | 2 字节二进制 `0xYY 0xZZ`：YY=位置 0-99、ZZ=速度 0-99；需先向 Command 特征写 `0x00` | 是 | **纯伸缩**无振动通道；SET 强度需映射为位置/速度；连接后需 init 握手钩子 |
| The Handy | **WiFi 本地 HTTP/WebSocket**（主路径） | 厂商本地 API（buttplug protocol `thehandy`） | 是 | 不在"ESP32-BLE 直连"射程 → 未来走 PC 侧 intiface/buttplug 网络分支 |

**要点**：同为"体感设备 B"，传输层（BLE vs WiFi）与语义（连续强度 vs 位置/速度）差异巨大，
因此框架必须保留"Profile 分派"这一扩展点，并区分 `transport=ble`（本次实现）与 `transport=wifi`（未来文档说明路径）。

参考：
- https://buttplug.io/stpihkal/
- https://buttplug.io/stpihkal/protocols/lovense/
- https://buttplug.io/stpihkal/protocols/fleshlight/
- https://buttplug.io/stpihkal/protocols/kiiroo/kiiroo-onyx-2
- https://github.com/buttplugio/buttplug （device-config-v4 + buttplug-rs protocols/ 参考实现）

## 6. 体感设备 B设备接入步骤（到货后按此操作）

> 一句话流程：**抓 UUID → 填 profile → 实现编码 → 编译烧录**。

1. **抓取协议**
   - 手机装 nRF Connect / LightBlue，连接目标体感设备 B，导出 Service / Characteristic UUID 表；
   - 打开厂商官方 App 操作（振动/伸缩/加热各档位），同时记录每次写入的字节（nRF Connect 的 Log/抓包功能，或 Windows Wireshark + BLE 抓包器）；
   - 先查 https://buttplug.io/stpihkal/ 对应品牌页 —— 很多机型已有文档，可"抄作业"；
2. **填 profile（占位→真实）**
   - 编辑 `esp32_firmware/toy_profiles.h`：替换 `MALE_MST_SERVICE_UUID_PLACEHOLDER` / `MALE_MST_CHAR_UUID_PLACEHOLDER` 为逆向所得 UUID；
   - 若有通知特征（状态回读）则补 `rx_uuid`，需要握手（如 Launch 写 `0x00`）则在 profile 预留 init 钩子（当前结构未含，可按需在 `ToyProfile` 增 `init` 函数指针并留 TODO）；
   - 按实物通道在 profile 表项里修正 `max_intensity` 与 `channels`（伸缩设备语义映射见 §6.1）；
3. **实现编码函数**
   - 编辑 `esp32_firmware/toy_profiles.cpp`：实现 `maleMstEncode()`，把
     `(intensity 0-100, waveform 0-3)` 编码为该机型协议字节（可参考 §5 已文档化协议）；
   - 多通道/伸缩类设备可能需要"周期性位置刷新"：在主 `loop()` 增加低频刷新钩子
     （与 `checkAutoStop()` 并列，10-50ms 级），并让 STOP/时长结束回中位或停写；
   - 语义映射建议（先按此规则，具体字节以实物联调为准）：
     | AI 输出 | 振动类（体感设备 A） | 伸缩类（待实物实现） |
     |---|---|---|
     | 强度 0-100 | ×60/100 → 0-60 档 | ×stroke_max/100 → 往复幅度/速度 |
     | 波形 constant/sine/pulse/random | 持续/正弦/脉冲/随机 | 全幅往复/平滑往复/短促抽插/随机序列 |
     | 时长 | `scheduleStop()` 自动停 | 同左（停止=归位或停写） |
     | STOP | 写强度 0 | 停运动（归位由实物决定） |
4. **切换 profile**
   - 把 `esp32_firmware.ino` 顶部 `ACTIVE_TOY_PROFILE` 改为 `TOY_PROFILE_MALE_MST`
     （或命令行 `--build-property build.extra_flags=-DACTIVE_TOY_PROFILE=TOY_PROFILE_MALE_MST`）；
5. **编译烧录**
   ```bash
   arduino-cli compile --fqbn esp32:esp32:esp32 esp32_firmware
   arduino-cli upload -p COM3 --fqbn esp32:esp32:esp32 esp32_firmware
   ```
   真机联调时把实测包贴在代码注释里存档，便于后来者核对。

### 6.1 语义映射注意（AI 单强度 vs 多通道/伸缩）

Tentacle HRV 的 AI 目前只输出一个 0-100 强度 + 时长 + 波形。对伸缩/多通道设备：
主通道按 §6 表格映射，其余通道（气压/旋转/第二马达/加热）默认随强度联动或保持关闭，
具体策略待实物后确定（可先在 profile 注释里写死规则）。加热通道默认**不开放**（烫伤风险）。

## 8. 风险与开放问题

1. 具体机型协议未知（无实物）→ Profile 框架先行，文档化协议（Lovense/Launch）作参照，实物 SOP 附上；
2. AI 单强度语义 vs 多通道设备 → 先"主通道映射，其余 profile 决定"；未来 server.py 可扩 SET 变体（方案 B 种子）；
3. 伸缩类需周期刷新位置序列 → `loop()` 预留低频刷新钩子位；
4. The Handy 等 WiFi 型不在 BLE 射程 → 文档标注 BLE/WiFi 两分支；
5. 加热通道安全 → profile 预留"默认禁止/上限"字段，先不开放；
6. 版权 → stpihkal CC BY-NC-SA，只概括引用并注明出处链接。
